# Production readiness audit — research-preview release

Scope: HSI research foundation plus read-only Aksh and Immunecity consumers. This audit hardens the implemented research preview; it does not establish completion of the full PRD, scientific validity, live clinical suitability or production organisation usage.

## Decision

Local public-preview builds and targeted integration gates pass, with automated checks added to all three repositories. This is not an unconditional production approval. Production deployment remains a coordinated, separately reviewed action. Database-backed verification is blocked by HSI network access and missing separate Aksh test-database configuration; consequential scientific/clinical use remains gated by source review, governance and the existing capability register.

## Findings resolved

| Finding | Change and evidence |
| --- | --- |
| Browser accepted weaker registry data than the CLI | Shared browser-safe structural validator; both runtimes verify SHA-256 revision payloads. Invalid metadata, unknown fields, spoofed identities and tampering fail closed. Production-preview browser test rejects a valid-looking record with a bad digest. |
| Source imports could lose concurrent updates | Exclusive file lock, fsync and atomic replacement; errors clean up owned temporary files. Tests prove contention does not change the existing registry. Killed-process stale locks require operator inspection rather than automatic lock theft. |
| Registry histories and timestamps were too permissive | Real calendar dates, explicit time zones, bounded record/history sizes, chronological revisions and duplicate-import detection. Corrupted input registries are validated before use. |
| Aksh accepted stale or unreleased snapshots | Release importer rejects older/conflicting timestamps and dirty producer revisions, preserves idempotency, serialises writers and leaves the existing snapshot untouched on failure. Local-change override is explicit. |
| ISI could mix individually valid releases | Required schemas and matching core generation timestamps are checked. Bundled release validation and recorded clean producer revision are CI gates. Remote requests have finite timeouts; invalid bundled data does not silently switch release. |
| Database isolation and TLS were too permissive | HSI requires its exact canonical endpoint/domain/database. Aksh and ISI refuse the HSI target; Aksh also refuses the ISI target. Remote connections verify certificates and reject insecure TLS modes. Wrong HSI hosts, protocols and databases are refused even with the project variable. Credential masking handles encoded delimiters and removes query/fragment values. `.env.local` precedence is corrected without overriding runtime configuration. |
| Aksh build depended on Google font downloads | Exact Fontsource package versions, local font assets and preserved OFL licence files. Full Next production build passes. |
| ISI had 136 type diagnostics and an incomplete test command | Real Bun types; strict JSON validation at DB/server-function boundaries; corrected imports, lookup-result shapes, optional data and LOINC mapping. Vitest and Bun-native suites execute separately under one command. Full type check passes. |
| Graph release version drifted from the source | Version now comes from extension provenance. Release tests track the current draft-ext-6 data. Connectivity retains a 99% gate for curated nodes without depending on draft nodes; draft contrast findings are not fabricated into connected science. |
| No repeatable branch checks | CI workflows install frozen dependencies and run tests, type checks and production builds. HSI also runs committed production-preview browser tests. ISI's tested clean installer resolves only its sandbox mirror prefix to the public registry while preserving versions and integrity hashes. |
| Static deployment swallowed unknown URLs | Known page rewrites only, client recovery view, baseline response headers and revalidation for scientific JSON. A regression test requires deployment routes to match registered app pages. Actual hosted HTTP behavior remains a post-deployment smoke check. |

Test adjustments correct obsolete fixtures and runner/type issues, not failed clinical assertions. In particular, private user-owned evidence collections remain deletable while shared evidence records are protected; graph connectivity does not require inventing links for draft contrast-finding nodes. No Gate C approval, knowledge-graph promotion or patient data was generated by this audit.

## Local verification

- HSI: 186 core tests pass; library/site type checks and production build pass; three production-preview browser tests pass (selected cited download, registry tampering rejection, route recovery/mobile layout). Validator and export generation are also checked in an isolated copy.
- Immunecity: complete TypeScript check and client/server production build pass. Full test command passes 295 Vitest tests and 335 Bun-native tests, including HSI release consistency and database-isolation checks.
- Aksh: strict consumer/import tests, database-target tests, capability-register consistency, complete TypeScript check and full Next production build pass. Tests cover unsafe/stale/dirty imports, duplicate import, lock contention and preservation of the current snapshot. The broader `npm run verify` runs workflow/rehearsal checks but stops at `patient-spine-db.test.ts` because the separate Aksh `DATABASE_URL` is unavailable. That command is failed/blocked, not passed; later database suites remain unverified. HSI credentials were explicitly removed for the run.
- CI workflows are committed, but their remote GitHub execution status has not been independently verified. Local checks are not a production deployment.

## Remaining release gates

1. **Neon connectivity and schema:** `DATABASE_URL` is now present and resolves to the canonical pooled HSI endpoint in `eu-west-2` / `neondb`. The proxy returned HTTP 403 before authentication. No SQL query or migration ran. The exact host `ep-hsi-production-pooler.c-2.eu-west-2.aws.neon.tech` was added to the environment draft without dropping the existing domains. Apply/save those settings; retry read-only connection, migration-ledger and table-shape checks when runtime policy changes. Do not treat a configured variable or unknown readiness observation as a successful connection.

   `db/verify/readiness.sql` provides the read-only ledger/table/constraint checks for the selected HSI branch's SQL editor. For cloud execution, the saved hostname rule covers HTTPS SQL access; native PostgreSQL clients also require an explicit TCP grant. No such TCP grant is currently configured. Do not assume an HTTP allowlist entry enables direct PostgreSQL.
2. **Coordinated release configuration:** deploy matching Aksh `/hsi` and ISI `/hsi/discovery` consumers before enabling HSI's connected links. Set `VITE_AKSH_APP_URL` and `VITE_ISI_APP_URL` to their production HTTPS origins at HSI build time. Validate the deployed links, JSON responses, cache headers and unknown-route 404s. No production origin was changed by this audit.
3. **Scientific provenance and rights:** initial registry records are locators, not fetched/verified metadata. Known seed support limitations remain visible. Metadata imports do not establish exact passage support, correction completeness, licence clearance or independent scientific evaluation. These are blockers for stronger scientific/clinical claims, not things a green build can certify.
4. **Private and clinical workflows:** authenticated persistence, tenant/organisation authorization with real permitted test accounts, retention and operational recovery need their own release evidence. Clinical/Aksh capabilities marked `in_validation` remain there. No patient-specific care, SSO, eligibility approval or shared database was enabled.

   Provide a dedicated Aksh non-production child-branch database in its own local/server configuration, with the required roles/schema, and rerun `npm run verify`. Never point it at HSI red-wave just to make a database test pass. ISI's real authenticated review/write paths likewise need their own permitted ISI test configuration; the passing unit tests do not replace that check.

For the current public read-only research preview, database credentials are not used by the browser. Do not expose them through Vite environment variables or static JSON. Keep database/authentication settings server-side and in secure environment settings. The cloud workspace's global `DATABASE_URL` belongs only to HSI: clear it (and `DATABASE_URL_UNPOOLED`) when starting Aksh or ISI previews, or supply each product's own correctly scoped server configuration. Connection guards now fail closed rather than silently using HSI's credentials for another product.

```bash
bun run test
bun run build
cd site

# immunecity, after its documented frozen installation
bun run typecheck
bun scripts/verify-hsi-release.ts

bun run build

# aksh-health-redesign/packages/platform-uk
npm ci --no-audit --no-fund
bun tests/hsi-research-contract.test.ts
bun tests/hsi-research-import.test.ts
bun tests/capability-status.test.ts
./node_modules/.bin/tsc --noEmit --incremental false

```

Use a disposable HSI source copy for `bun run check`/`bun run outputs` when protecting tracked site snapshots from timestamp refreshes. See the separate integration runbooks for export/import steps. Do not run migration or seeding scripts as part of the checks above.
