# P0-B isolated staging operations — implementation and acceptance

12 November 2026. Builds on P0-A (#279) and the hardened transport/context fixes (#280). This is an engineering implementation and operator handoff, not proof that a source authority is independently operating, terms have been agreed, credentials exist, two real provider deployments were exercised, or P0-B has passed. The assistant has made **zero real model requests** and no production configuration, database or approval changes.

## Delivered code

| Component | Implementation evidence | Boundary |
|---|---|---|
| Independent source adapter | `src/researchV2/operationalSourceClearance.ts` consumes a trusted authority lookup, existing pinned Ed25519 receipt verifier and protected store. Source/version/passage/action/signature/freshness/revocation must pass. Explicit cleared/unknown/expired/corrected/retracted/withdrawn/identifier-conflict/revoked outcomes; no grant is inferred from a title, open URL or model | No authority endpoint, signing key, policy or independent operator is invented or deployed |
| Dependency invalidation | Register artifact dependencies only after stored clearance. Failed/withdrawn/revoked clearance flags dependent artifacts, including registration races. `refresh(sourceId)` can reconcile authority status without storing passages; no automatic artifact reapproval | An operator must connect actual revocation/withdrawal events or schedule refresh. No scheduler or downstream publication recall is claimed |
| Protected source and run receipts | `stagingOperationStore.ts`: private owner directory/file, no-follow file opening, exclusive writer lock, bounded append-only API, hash chain, file/directory synchronization, corruption/truncation refusal and poisoned-write handling. Reservation updates serialize through the same store handle and survive reopen | One operator-controlled persistent staging filesystem only. Not Vercel ephemeral storage, distributed quotas, WORM storage, an authenticated audit signature or a demonstrated database restore. Filesystem owners could rewrite/recompute a chain; protect independent backups and signed authority records |
| Independent provider approval | `stagingDeploymentApproval.ts` verifies pinned Ed25519 signatures over exact deployment/configuration/terms/source-policy bindings, isolated-staging scope, ≤24-hour validity, bounded authority lookup and revocation checks; a signed approval receipt must be acknowledged by the protected store before authorization succeeds | Verification only; no approval issuer or real signed approval is supplied. Production callers must use a trusted verifier/authority, never browser booleans |
| Provider wire integration | `stagingProviderOperations.ts` implements OpenAI Responses and Anthropic Messages request/response codecs behind the pinned native HTTPS transport. Records actual header request IDs, response IDs, resolved model ID and usage; incomplete/refused/malformed outputs are rejected. Resolved model must match the approved configured model; no silent alias drift | No model name/deployment is approved by the code. Test names are explicitly synthetic. Transport overrides are trusted test seams, never request parameters |
| Budgeted run service | Disabled by default. Independent approval and source policy must match; reserve cost units and acknowledge start before dispatch. Recheck clearance and deployment approval after start. Set output cap, bound request/response size and deadline, settle external cancellation, retain reservations after uncertain outcomes. Terminal storage acknowledgement is required before returning completion | Configured unit prices must conservatively cover the approved model's current input/cache/output charges. UTF-8 wire size plus framing allowance is a conservative engineering input bound, not a vendor tokenizer/billing guarantee. Usage beyond bounds rejects the result and raises a recorded breach. No automatic retry/refund; provider account spending limits and accepted pricing evidence are still required |
| Redacted replay/recovery | `stagingReceiptReplay.ts` checks lifecycle binding/duplicates and projects hashes, IDs, usage, reservation and status. Missing finishes are `completion_unknown`; orphan reservations are surfaced. Replay never retries, approves science or marks live smoke accepted | Metadata replay only. Reconstruct permitted inputs from the independently governed source/version and verify hashes; raw provider content is not retained in operational receipts |

Provider run receipts contain no prompt, passage, claim, output span/rationale, credentials, headers or raw errors. The protected source-receipt records retain signed licence/attribution metadata, not passage text. Approval and source IDs/references must themselves be non-secret metadata. The journal's recursive payload-key guard is defense in depth; it is not a general-purpose secret classifier. Do not send arbitrary request objects to its trusted append API. Source metadata must come from the approved authority, not model text. No telemetry destination or public log sink is added.

`dispatchAttempted` means the transport was invoked, not that the remote provider received or completed the request. Completion additionally requires a successful validated response, real request/response identifiers, usage bounds, exact model identity and acknowledged terminal receipt. Neither event establishes scientific correctness, model independence or graph publication approval.

## API contract references

Wire codecs were checked against the official [OpenAI Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create) and [Anthropic Messages API](https://platform.claude.com/docs/en/api/messages/create). OpenAI requests set `store:false`; this flag is not a substitute for agreed provider retention/data-handling terms. Anthropic API version is an explicitly approved configuration value. No prices, model availability or legal permission are inferred from these references.

## Offline verification

`test/stagingProviderOperations.test.ts`, `test/stagingDeploymentApproval.test.ts` and the existing `providerReliability.test.ts` exercise real temporary private filesystem persistence, fresh synthetic authority keys, fixture provider envelopes and injected faults. They cover all requested source states; expiry and identifier conflicts; signature/revocation denial; dependent-artifact withdrawal/revocation flags; default-disablement; missing/revoked deployment approval; durable-start/terminal failures; timeout, 429, 5xx, malformed/schema response, overflow, cancellation and budget exhaustion; excessive usage; concurrent reservations, single-writer lock, reopen recovery and corruption/truncation. Redaction checks assert credential, passage, claim and rationale markers are absent from journal output. No fixture result is SME gold or a real provider smoke.

## Practical operator sequence

1. Fill the deliberately unapproved `operations/p0-b/approval-template.v1.json` outside public source control with references and non-secret IDs. Keep credentials, actual private pins, authority private keys and protected file locations in the approved private environment. The template has no authority to approve anything.
2. Source-policy owner selects the source authority and exact version/passage/action policy. Validate corrected/retracted/withdrawn and conflicting records against real authority behavior. Independently pin public keys and configure source verification/revocation. Licensed data requires actual applicable partner authorization; public-source tests require appropriate source policy, not an invented MoU.
3. Independent provider/data-handling owner approves each normalized deployment configuration, exact model, API version, terms reference, source-policy reference, pricing upper bounds and total cap. Use the service's canonical configuration hash in a signed staging approval. Approval records must remain current and revocable.
4. Run one staging worker with a private persistent journal. Inspect existing chain/lock and unresolved starts before any restart. A stale lock after a crash requires operator investigation; do not automatically remove it or retry uncertain charged requests. Configure a source invalidation watcher/refresh job and independent backups; no such jobs are created here.
5. Configure `createOperationalSourceClearance` with the real authority, cryptographic verifier and journal. Configure `createStagingDeploymentApprovalVerifier` with independent public keys, receipt resolver and revocation lookup. Pass its `authorize` function to `createStagingProviderOperations`. Leave `transportFactory` unset so native pinned HTTPS is used; credentials come only from the server credential resolver. Enable only this isolated staging service after the approvals above.
6. For each approved deployment, run one independently cleared non-PHI synthetic/public-source task under the approved cap. Save protected metadata receipts, exact configuration/build references and independently inspect request ID, response ID, resolved model and usage. Use returned content only within its permitted handling scope; retain no source text in operational logs. Replay verifies identity/hashes and incomplete work without automatic resubmission.
7. Run controlled fault checks on the actual runtime; confirm unknown/expired/revoked source or approval denies egress and flags dependencies. Account for charged unknown outcomes. Obtain independent operator/security/source-policy acceptance. Record real smoke results separately; keep scientific and graph-promotion flags false.

Live approval/model/credential references were requested from the user and remain required for dependent execution. No secret values should be pasted in chat. The assistant cannot truthfully mark this phase accepted until the two approved real requests and independently operated authority/store evidence exist.
